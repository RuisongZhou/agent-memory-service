# Mem0 V3 消息处理与存储边界修正

> 历史设计记录：文中的双策略代码及 Memos 对照属于 [`codex/mem0-memos`](https://github.com/RuisongZhou/agent-memory-service/tree/codex/mem0-memos)（拆分点 `971ac13`）。当前 main 仅支持 Mem0；部署和 API 以 [当前配置参考](../api.md) 为准。历史实验数字与协议未改写。

历史记录：本文是第一轮Python OSS 2.2.1对照。用户随后明确目标为Node SDK 3.3.1，并要求实体索引和混合检索一起对齐；当前实现以[3.3.1设计与实现](mem0-sdk-3.3.1-alignment.md)为准。本文的Unicode字符计数、纯语义检索及评测数字不代表新版本。

日期：2026-10-14。对照范围：Python OSS `mem0ai==2.2.1` 内的 V3 ADD-only 管线、默认 `infer=True`。V3 是处理管线名称，不等于 Python 包的主版本号。本文不推断 Mem0 托管平台的内部实现。

## 1. 现有方案是什么

服务接收 `messages` 后，先将完整输入和任务保存到 `requests`；形成工作器按 `inputSeq` 处理，读取相关旧事实和历史消息，调用一次提取模型，再将新事实、向量、批次来源和 `formed=true` 一起提交。向量缓存发布后才返回 `searchable=true`。`infer=false` 直接保存文本事实，跳过提取模型。

逐项核对官方源码和修改前代码得到以下结果：

| 处理位置 | 官方 Python OSS | 修改前服务 | 判断 |
| --- | --- | --- | --- |
| 本次新增消息 | `parse_messages` 拼接角色与全文 | 拼接角色与全文 | 基本一致，没有300字符截断 |
| 历史消息 | 最近10条，每条提示词内容最多300个Unicode字符，截短后加`...` | 同样取10条、截300字符 | 长度规则一致，历史来源不同 |
| 空历史消息 | 先取10条，再跳过空role/content | 输出空内容的角色行 | 存在格式差异 |
| 历史作用域 | 调用时实际提供的user_id/agent_id/run_id组合 | tenant内按platform/project，不过滤session | 我们的会话标识没有参与历史隔离 |
| 原始写入 | `infer=False` 提前返回，不写消息历史 | 下次提取仍可从requests读到它 | 原始写入被再次当作对话上下文 |
| 失败提取 | LLM调用抛异常时，不执行后续save_messages | 失败任务也在历史候选中 | 未完成的输入被当作已处理上下文 |
| 成功但无记忆 | 保存消息历史 | requests保留输入，形成成功 | 应继续支持后续指代 |
| 原文存储 | SQLite消息表保留最近10条完整消息 | requests长期保留完整输入 | 有意保留更完整的审计来源 |

官方也有自己的失败边界：该版本解析错误可能按空提取处理，部分存储错误路径会保存消息历史。我们保留严格契约和原子事务，不复制这些容错行为。

源码依据：[官方形成管线](https://github.com/mem0ai/mem0/blob/v2.2.1/mem0/memory/main.py)、[消息格式化](https://github.com/mem0ai/mem0/blob/v2.2.1/mem0/memory/utils.py)、[历史裁剪与提示词构造](https://github.com/mem0ai/mem0/blob/v2.2.1/mem0/configs/prompts.py)、[消息历史存储](https://github.com/mem0ai/mem0/blob/v2.2.1/mem0/memory/storage.py)。下载快照及SHA-256保存在本地评测目录，避免仅凭可变网页判断版本。

### 三种截断不能混用

1. 历史提示词的300字符裁剪：只为指代提供有限上下文，不改原文，不作用于新消息。
2. 本地嵌入模型的512-token限制：影响召回查询或记忆的向量表示，不会把同一文本交给提取LLM的内容缩短。长输入尾部可能无法影响旧记忆召回，这是另一个需要独立评估的问题。
3. `maxMessageBytes` 的8KB头尾视图：属于Memos形成逻辑，不应迁入Mem0。本次固定案例用超过8KB的中英文/emoji混合消息检查新消息全文传递。

`mem0MaxTokens` 限制模型输出；API的`text`入口另有4096字节上限。这两者也不是`messages`的新消息截断规则。

## 2. 我们的目标

每次提取只将本批消息视为新增材料；历史区只用于解释同一会话的指代。原始输入不因提示词预算被修改；原始写入不会悄悄变成后续智能提取的历史输入；失败任务保留审计材料，但不冒充已成功处理的上下文。

长期事实仍然在项目范围内复用。将历史消息按会话隔离，不意味着用户换会话后无法检索同项目事实。

## 3. 为什么现有方案不能达成目标

旧实现从任务表读取历史，实际上把“已收到输入”等同于“可用的会话上下文”。任务表同时包含其他会话、直接写入和失败输入，所以最后10条未必是本会话已经处理的10条。提取模型可能据此错误消解“它”“继续按刚才的方案”等指代，错误随后会持久化为新记忆。

仅调整字符数量不能消除问题；将所有新消息也截到300字符反而会永久丢失本批可提取的信息。存储中保留了原文，也不代表遗漏的信息曾进入LLM。

## 4. 设计方案与本次实现

### 4.1 明确三层数据

| 数据 | 用途 | 保存与裁剪规则 |
| --- | --- | --- |
| `requests.inputMessages` | 原始输入、重试和批次来源 | 完整保存，失败或raw也保留 |
| 提取上下文 | 本次LLM输入 | 新消息全文；合格历史的最近10条，每条前300字符 |
| `memories`、向量、`mem0_sources` | 长期事实和检索 | 保存提取结果或显式raw文本；原子提交并保留来源 |

不新增冗余的历史消息表，利用已有有序输入和形成事务状态确定可用窗口，避免历史表与记忆提交出现新的同步问题。

### 4.2 历史候选条件

在tenant自身存储内，查询必须同时满足：

- platform、project、session与当前任务相同；
- `inputSeq` 小于当前任务，消息数组非空；
- `infer`不是false；旧记录缺失此字段仍按既有默认true解释；
- `formed=true`，状态为`indexing`或`completed`。

`formed=true`与记忆/来源同事务提交，是上下文资格依据。已提交、尚未发布缓存的`indexing`允许用作上下文；不需要重新调用模型。成功提取0条也设置formed，因此不会丢失对后续有帮助的会话内容。

先查询最新10个合格非空批次，再按顺序展开，取最后10条消息。每批至少一条，10批足以覆盖最后10条。空内容消息仍占窗口位置，但格式化时不生成角色行，与官方顺序一致。按Rust `chars()`裁剪，对应Python Unicode字符切片，不按UTF-8字节截断。

**作用域映射属于服务设计选择。** 官方只会按实际传入的entity组合隔离；只传user_id时，其历史自然跨业务会话。本服务API已经要求session，因此将它加入会话上下文键。官方SDK若使用run_id，长期事实也受该过滤条件影响；本服务的长期事实继续按project可见，不能据本次上下文对齐宣称全部检索语义等同SDK。

### 4.3 调用和存储约定

调用方提交尚未处理的完整消息批次，保留user/assistant角色及真实时间戳，用稳定turnId重试。不要反复提交滚动的全量对话历史；新旧区划分由服务完成。异步写入拿到requestId后，依赖记忆前必须等待formed/searchable。

`infer=false`表示直接写入一条可检索记忆。因此raw文本仍可能作为相关旧记忆出现在`Existing Memories`；本次保证的是它不再进入`Last k Messages`，并不把raw记忆从检索中隐藏。

不修改项目事实范围、内容去重键、角色归属、ADD-only逻辑或输出契约。`linked_memory_ids`继续只是当前契约校验字段，不宣称本次实现了关联图。旧事实的纠正仍通过显式管理接口完成。

### 4.4 代码责任与部署

- `memory-rules::mem0`：新消息全文与历史窗口/裁剪的纯函数。
- `memory-algo-mem0::repo::previous_inputs`：数据库过滤及顺序。
- `memory-algo-mem0::formation::form`：传递session、拼装提示词及现有形成事务。
- HTTP/MCP、公共运行时、存储引擎和Memos保持既有职责。

不新增配置、不改schema、不删现有数据。重启采用新代码的Mem0服务即可使用新窗口规则；部署仍使用`.env.example`、`examples/service-config.json`、`docs/api.md`和现有CI工作流。

旧版本已经形成的错误事实不会自动修好。应先用`mem0_sources.inputRequestIds`定位来源，再显式纠错；需要重建时，在独立新存储中按原输入顺序回放和比对，审核后再切换。不要直接覆盖当前库，也不要把旧基准分数标记为本次修复的结果。

超出提取模型上下文的大请求，后续应采用明确预算拒绝或保留消息/偏移来源的分片处理；本次不引入无记录截短或新的自动分片算法。嵌入召回的长消息覆盖也单独立项，不凭本轮边界样本调整阈值和topK。

## 5. 验证方案

独立评测入口：`eval/mem0_v3_context.py`。比较修改前HEAD、修正代码与真实安装的官方SDK。三组使用相同冻结消息和隔离空存储，模型生成由同一提示词敏感替身代替；服务使用mock向量，SDK使用固定向量和本地Qdrant，SDK实体抽取/词形还原被显式替换。所有模型网络地址限定回环，真实模型调用为0。

场景覆盖：超过8KB新消息与尾部信息、300字符Unicode历史视图、跨会话隔离、raw绕过、零记忆成功上下文、跨批最近10条、同会话指代和空消息窗口。额外检查服务端完整原文、错误来源是否持久化和记忆是否立即可查。HTTP回归另外覆盖真实失败耗尽、两次重启后的上下文；原有HTTP回归覆盖输出修复和来源链。

边界对照还发现官方SDK的实现限制：`save_messages`为同批消息写入同一个created_at，淘汰和读取只按该字段排序，无批内顺序作为第二排序键。在本地固定11条单批案例中，SDK保留了较早消息而非真正最后10条。本服务继续使用inputSeq与数组顺序，不复制此问题。该结果属于本轮实测，不能概括所有SDK版本或存储环境。

完整原文检查显式使用`list_turns(tokenBudget=20000)`。默认读取预算会跳过放不下的完整批次，不能由默认结果中缺少长批次推断数据库丢失原文。试运行报告也保留：首轮用了默认读取预算，随后修正了检查方式；最终三组协议与脚本指纹一致。

这是一组消息处理/持久化语义评测，不是自然语言提取准确率，也不测模型速度或数据库吞吐量。每项断言和原始请求/响应都保存，不能把全部通过换算成LoCoMo准确率。下一轮真实模型评测应另外冻结会话作用域映射、同样的语料/问题/模型/上下文预算，继续使用独立空库；不能直接与历史全量成绩拼接。
